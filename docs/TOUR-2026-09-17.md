# The first end-to-end run — a guided tour, 2026-09-17

What happened when the owner used the product as a customer for one day, stage by
stage: what each screen is for, what it was asked to do, what it actually did, and
what that taught. The checklist that framed it is `docs/E2E-ERSTLAUF.md`; every
defect found is in `ROADMAP.md › LATER › First-run findings` with a B-number.

**The one-line summary.** 81 roadmap items were done and 1179 tests were green, and
the product could not be signed up for. Five defects were closed during the run and
eleven more were written down. None of them were findable by a test suite, because
a test suite only asks the questions somebody thought to write down.

---

## What the product is, in one paragraph

A shoebox of receipts and an expensive person who sorts them once a year. This is a
robot that does the sorting. Money never disappears — it moves from one labelled
drawer to another, and every booking touches exactly two drawers: one receives
(*Soll*), one gives (*Haben*). A tank of petrol for CHF 58.48 is `Soll 6210
Betriebsstoffe / Haben 1020 Bankguthaben`. The whole of bookkeeping is that line,
repeated. The robot's job is to write it without being told, and to learn from the
corrections when it gets it wrong.

Four rooms, in the order work moves through them:

| Surface | Its question | What happens there |
|---|---|---|
| **Heute** | Was muss ich tun? | The fridge note. Decisions, not numbers. |
| **Belege** | Was ist reingekommen? | Paper goes in — photo, e-mail, or an invoice you write |
| **Bank** | Was ist passiert? | The statement arrives; the memory game (*Abgleich*) pairs money with paper |
| **Abschluss** | Ist alles sauber? | Month check, VAT quarter, year end, and one zip for the Treuhänder |

Plus **Mehr**: Lohn, Modell, Kontenplan, Überprüfung, Audit.

## Stage 0 — before anything ran

Two things were true and neither was visible from the code.

**A live credential was in the pushed history.** The Postgres password printed by
`make dev` that morning was in `scripts/setup.sh` across a dozen commits on a pushed
branch. Not an old secret — the one the running database used. Rotated first
(changing the credential is what closes it; rewriting history is hygiene that comes
after), together with `JWT_SECRET`, `SECRET_KEY` and both compose passwords.

Found in passing: **`JWT_SECRET` silently overrides `SECRET_KEY`** (`config.py:170`),
so rotating only the latter would have changed nothing — and that key also signs the
model blobs (B-34), which is the only thing standing between a stored `.pkl` and
`pickle.loads`.

**The run was done on compose, not `make dev`.** `make dev` connects as a Postgres
superuser and prints a warning saying Row-Level Security therefore enforces nothing.
Testing the product's central promise on a connection exempt from it is not a test.
That decision is what surfaced Stage 1.

## Stage 1 — registration · **the product could not be signed up for**

`POST /api/auth/register` creates a tenant, then seeds the default chart of
accounts. `kontenplan` is one of the 24 tables RLS covers, and nothing on that path
established the tenant context, so Postgres refused the insert:

```
new row violates row-level security policy for table "kontenplan"
```

The only way to create a first account, broken in the only configuration meant to
ship — since B-24. Three things hid it: every test connects as the table owner, for
whom policies do not apply; `make dev` runs as a superuser; and `sso.py` had done the
right thing since B-36 while `/register`, the older endpoint, was never brought
along. Two paths create a tenant; one was updated. → **B-82**

**And a second defect hid the first for two hours.** The browser reported *"blocked
by CORS policy"* while CORS was configured correctly. `RequestContextMiddleware`
builds the 500 response itself and sat *outside* `CORSMiddleware`, so that response
carried no `Access-Control-Allow-Origin` and every server error reached the client as
a CORS failure. The comment three lines above it states the principle correctly for
the 413 case; the next line broke it for errors. → **B-83**

Also here: `docker-compose.yml` allowed only `http://localhost:3000` while
`config.py`'s own default allows `127.0.0.1:3000` as well — a deployment file
narrowing the code's safe default. And `errors.ts` mapped every `ERR_NETWORK` to
*"Läuft das Backend?"*, the one explanation that was not true.

**Lesson.** A test suite that runs as the owner cannot see a policy that applies to
everyone else. And an error path outside the middleware that decorates responses
will lie about every failure downstream of it.

## Stage 2 — Kontenplan · teaching the robot its drawers

A new tenant gets 16 default accounts. The owner's real business uses 39, extracted
from 762 of his own 2024 bookings and imported through the B-20 wizard: **27 neu · 4
geändert · 8 unverändert · 0 nicht gelesen** → 43 accounts.

The wizard is a wizard and not a button because `PUT /api/kontenplan/` replaces the
**whole** plan. Reading and writing are separate requests, the preview names what
would disappear, and *Ergänzen* — the mode that cannot lose data — is the default.
That design held up under a real file.

**The four `geändert` rows were the most valuable thing on the screen**, because they
are the product's generic label against a real Treuhänder's:

| Konto | The product ships | The real ledger says |
|---|---|---|
| 5700 | AHV, IV, EO | AHV, IV, EO **Inhaber** |
| **6200** | **Fahrzeugaufwand** | **Reparaturen, Service Fahrzeuge** |
| 6500 | Verwaltungsaufwand | Büromaterial und Drucksachen |
| 8900 | Direkte Steuern | Kantons- und Gemeindesteuern |

The owner asked the right question: should the split accounts be merged into 6200?
**No — and the data settles it.** Across 135 vehicle bookings by his accountant:
6210 Betriebsstoffe carries VAT (82 of 91 lines at `I81`, 8.1 %), while **6220
Fahrzeugversicherung is 5 of 5 and 6230 Verkehrsabgaben 6 of 6 with no VAT code at
all** — insurance premiums are exempt, road tax is a sovereign levy. Collapsed into
one account, that account is half taxed and half not: the classifier cannot learn a
rate for it and B-67's *"Aufwand ohne Vorsteuer"* hint fires forever on every
legitimate insurance payment. **The split carries the VAT.** → **B-84**

Found in the same import: the seed puts Geschuldete MWST on `2200`, real charts use
`2205`, and after *Ergänzen* the tenant holds both with byte-identical
descriptions. → **B-85**

## Stage 3 — training · showing it last year

762 bookings imported, model trained automatically. **86.7 % cross-validation, 37
account classes, 182 memory entries.**

Ten rows were dropped and all ten were Banana's own header and metadata rows — no
real booking lost. That was the day's first check that simply passed.

**What 86.7 % means.** Random over 37 classes is 2.7 %; always guessing the most
frequent account is 23 %. So it is a real result. But cross-validation asks *can it
reproduce what the Treuhänder already did*, not *will it get tomorrow's receipt
right* — and repeat vendors are answered by the memory layer before the model is
consulted at all.

**The test that proved it.** Typing `Agrola, TS` — a string that appears 91 times in
the training data — returns *Gedächtnis · 6210 · 100 %*, with the model agreeing at
89 %. Typing the real receipt line, `LANDI THULA TopShop Matzingen BLEIFREI 95`,
returns the right answer at 72 % — but from **Regeln**, the keyword fallback. The
model's own top five reads *5820 Spesen 22 %, 6210 14 %, 6500 14 %*: it puts the
wrong account first. The layered pipeline worked exactly as designed, and that is the
point — **the figure the page leads with belongs to a layer that was not
consulted.** → **B-88**

Found while reading the import result: the page reported **182** memory entries in
its KPI card and **364** in the import box, three centimetres apart. The count added
the new entries to a set that already contained them. Not cosmetic — the same number
goes into the audit row, and B-17 ships that table to the Treuhänder. → **B-86**

## Stage 4 — one real receipt · **the first end-to-end success**

A phone photo of a thermal till receipt — Landi/Agrola, fuel, past the EMV hashes and
the barcode, no QR code anywhere.

| | Expected | Read |
|---|---|---|
| Lieferant | LANDI THULA | Landi ✓ |
| Betrag | 58.48 | CHF 58.48 ✓ |
| Datum | 07.11.2025 | 07.11.2025 ✓ |
| Konto | 6210 / 1020 | 6210 / 1020 ✓ |
| MwSt | I81 | I81 ✓ |

Five for five, and it left `Fällig` empty rather than inventing a due date.

**But it filed the receipt as an open payable.** The receipt says `Erhalten:
MASTERCARD` — the money left the account at the till. The Belege page reported *"OFFEN
CHF 58.48 · 1 Rechnung"*, next to a card headed *Fälligkeitsdatum überschritten*. One
`status` carries two meanings: on the Belege list `offen` reads as *not yet
reconciled*, which is true; on Offene Posten and Heute the same rows are presented as
*"Was schulden wir"*, which for this row is false. Scan a month of fuel receipts and
Heute invents a debt. → **B-89**

## Stage 5 — the bank statement · where the product meets its limit honestly

A real UBS April statement: **28 transactions parsed, 21 marked `unsicher`.**

The model lives in two worlds, and the line between them is whether the bank text
names a counterparty:

| Bank text names someone | | | Bank text names nobody | |
|---|---|---|---|---|
| Cembra Money, Leasing | → 6260 | **92 %** | E-BANKING-SAMMELAUFTRAG | → 6500 at 35 % |
| Santander Consumer Finance | → 6260 | **92 %** | ZAHLUNG DEBITKARTE | → 6500 at 35 % |
| Sarah Mäder, Miete Lager | → 6000 | **92 %** | | |
| Die Post | → 6513 | 67 % | | |
| Swiss Life ×2 | → 5720 | 61 % | | |

**14 of 28 lines — half the statement — were proposed as `6500`**, an account that
appears in 8 of his 762 real bookings (~1 %). The lines genuinely cannot be resolved
from the bank text; B-63 says so and the Abgleich exists to resolve them against
invoices. What does not follow is filling the field anyway: a pre-filled account gets
accepted, a blank one gets looked at. **The product already holds the opposite
principle in writing** — B-67, on the VAT return: *"Ziffern, die kein Buchungssatz
hergibt … stehen sichtbar auf 0.00 statt geraten zu werden."* → **B-92**

And beside the words «21 unsicher» sits a single button, **«Alle AI-Vorschläge
übernehmen»**. One click, 14 wrong bookings. → **B-91**

*(The second half of this stage — the Abgleich itself — needs the invoices behind
those Sammelaufträge. Continued on the next run.)*

## Stage 7 — Lohn · the best-written screen in the product

Opened with no configuration, the page refuses to work and says exactly why:

> *Noch nicht bereit. Es fehlen: UVG NBU-Satz, UVG BU-Satz, FAK-Satz,
> Verwaltungskostenbeitrag.* … *ohne sie wird keine Abrechnung erstellt, weil eine
> geschätzte Prämie wie eine richtige aussieht.*

All four missing rates named at once, not one at a time. Where to find them, stated:
*"stehen im Vertrag mit Ihrer Versicherung oder werden vom Kanton bestimmt"*. The
federal rates that *can* be defaulted are defaulted **and cite their source** — AHV/IV
Merkblatt 2.01 and 2.08, with the date the figures were last checked and a note that
they are re-set each January. Empty voluntary insurances mean *not insured* and the
line simply does not appear. A month can be settled once; a correction is a new
payslip, not an edit. And the yearly summary says on its face that it is **not** a
Lohnausweis — that is official Formular 11.

This is the page that knows it cannot guess. It is worth putting next to Stage 5,
where the product guesses a 1 % account onto half a bank statement: **the same
codebase, two opposite instincts, and only one of them written down as a principle.**

Two findings here. The pension contribution on the real payslip is **9.9 % of the
full salary with no Koordinationsabzug** — correct for a plan *ohne
Koordinationsabzug*, wrong for BVG-minimum, and nothing says which is meant
(→ **B-94**). And the BVG card reports *"Kein Widerspruch zum Obligatorium
gefunden"* on a tenant with zero employees: green because there is nothing to check,
the same shape as an RLS check passing on an empty database (→ **B-95**).

## The pattern

Most of the day's findings are one shape: **two places, each defensible alone,
disagreeing about the same fact.**

| | One side | The other |
|---|---|---|
| B-83 | `docker-compose.yml` CORS | `config.py` CORS default |
| B-85 | `seed_tenant` → 2200 | real Swiss charts → 2205 |
| B-86 | import result → 364 | KPI card → 182 |
| B-87 | Heute reads `best_vision` | Modell reads `available` (does not exist) |
| B-90 | sidebar says *Buchungen* | page title says *Insights* |
| B-92 | B-67: never guess a figure | Kontierung: guesses anyway |

B-87 is the sharpest of them: two hand-written TypeScript interfaces for one
endpoint, one of them naming four fields the API has never sent — so that card could
not report anything but "Nicht verbunden", ever. It is precisely the failure B-59
existed to end, surviving on the single endpoint B-59 did not touch, protected by a
stale comment claiming the endpoint was untyped.

**This is not a coding problem. It is a problem of two sources of truth for one
fact,** and it deserves a sweep of its own once the tour is finished.
